CAP App — development overview

27 September 2026 · Local working prototype

What we achieved

CAP now has a working connection between its browser interface and a Java Spring Boot backend. A coach can create a workout, assign it to the example athlete, and have that athlete record a timed training session. Finished sessions are saved with their actual sets, repetitions and weights. Records are tracked by exercise and rep count, and coaches can use those records to prescribe weights.

The project is still a local demonstration, not a production service. The coach and athlete accounts are simulated. Planning, bookings and shop management are browser previews; they are not yet connected to the Java backend.

Frontend work

We built one responsive HTML/CSS/JavaScript application for phones, tablets and desktops, with Dutch interface text and English code identifiers. CAP's existing site and the supplied Trainin screenshots informed the feature list. The app has its own styling, light and dark themes, CAP branding and a Stronger Together welcome screen.

The frontend includes:

  • Athlete and coach preview dashboards with useful session summaries.
  • A sidebar with Planning, Bookings, Workouts, athlete/group overviews, a training log and Shop. Available links depend on the preview role.
  • A profile dropdown with Settings and clearly labelled account-feature previews.
  • Login and signup design previews, draft terms/privacy panels and optional marketing controls. No real registrations or credentials are stored.
  • Coach forms to create workouts, search exercises and assign a workout to the example athlete, Guillaume.
  • Local-browser previews for managing class times, capacity, bookings, attendance, products and prices.
  • An actual Java connection indicator under Settings.

Mobile layouts stack fields and cards, use readable inputs and comfortable touch targets, and retain the existing compact Menu control. Real-device testing, including the iPhone keyboard and long dropdowns, remains outstanding.

Backend work

We introduced a separate Maven/Spring Boot project in backend, using Java 21. The Java 11/21 mismatch was diagnosed and the workspace's new VS Code terminals were configured for the installed Java 21 JDK.

The original src folder remains the earlier console learning project. Its workout classes and file-saving exercises helped establish the data flow. The Spring Boot code now uses structured API models suited to the web application. The console workouts.txt is not automatically imported into the web backend.

How the pieces communicate

  1. A person clicks a button or fills in a form in the frontend.
  2. JavaScript uses fetch() to send an HTTP request to Spring Boot.
  3. A Java controller receives the request as structured data.
  4. The storage/service code validates it, computes any records or percentage targets, and saves it.
  5. Spring returns JSON and the frontend displays a Dutch result.

Terminal System.out.println messages are developer output. They are not the messages displayed in the website. The frontend controls the user-facing text.

Endpoint Purpose
GET /api/health Test the connection
GET /api/workouts Load saved workout plans
POST /api/workouts Validate and save a plan and optional assignment
GET /api/training Load completed session history
POST /api/training Validate and save a finished session
GET /api/records Calculate best weight for each exercise/rep count

CORS allows the local frontend origin http://127.0.0.1:5500. This is a browser access rule, not authentication. The backend binds to the local computer.

Training flow

Coach

Create a workout with a name, description and exercises. Each exercise has planned sets and reps, plus one of three weight choices:

  • No target weight.
  • A fixed weight in kilograms.
  • A percentage of the assigned athlete's record for the same exercise and rep count.

Assigning a new workout for today replaces today's previous assignment, while keeping the older workout in the library. Coaches need no subscription to use their tools. Actual staff authorization still needs to be implemented server-side.

Athlete

Open an assigned workout or a workout from the library and click Start training. The timer uses a saved start timestamp, so it continues across navigation and refreshes rather than depending on the browser counting every second.

Enter actual reps and kilograms for each completed set. Add or remove sets as needed. Planned figures stay separate: leaving an exercise with no sets means it was skipped. At least one completed set is required to finish. A running draft can also be explicitly discarded without changing completed history.

Click Training afronden to stop the timer and save. The overview shows elapsed time, original prescription, actual results and new records/first registrations. The same information remains in Trainingslog for the athlete and coach.

If saving fails, the draft stays available. Retrying uses the same session ID, which prevents a lost response from creating duplicate completed sessions.

PR and percentage rules

Records are per exercise name and exact rep count, for the one example athlete. A 60 kg squat for 5 reps is separate from a 70 kg squat for 3 reps. A later 62.5 kg set for 5 reps improves the five-rep record. Equal or lower weights do not beat it. Only finished sessions count. A first recorded result establishes the baseline.

Example: 90% of a 60 kg five-rep squat record is 54 kg. Java calculates and saves both the reference record and the resulting target when the coach saves the plan. Later PRs do not silently change that saved prescription. Targets are rounded to two decimal places, not to equipment increments. A coach can choose a practical fixed weight instead.

If no matching rep record exists, the percentage plan is rejected with an explanation; the coach can use a fixed weight. These are rep-specific records, not estimated one-rep maxes. Use consistent exercise names and weight conventions (for example, total barbell weight versus weight per dumbbell). Name matching ignores letter case and repeated whitespace, but different exercise names remain different records. Zero kilograms means no added weight, not measured body mass.

Where information is saved

Backend writes use a temporary file and an atomic replacement. The in-memory state updates only after writing succeeds. Backend data, build outputs and test logs are excluded from Git; they are not published to GitHub. Back up backend/data separately if you want to preserve local example workouts and results.

How to run it

From the backend folder, with Java 21 selected:

.\mvnw.cmd spring-boot:run

Wait for Started BackendApplication. Open frontend/index.html with VS Code Live Server, then visit http://127.0.0.1:5500/frontend/index.html. Use Open ontwerp-preview zonder gegevens. Choose Coach to create/assign workouts and Sporter to start and finish them. View Trainingslog for history and PRs.

Spring Boot runs until stopped with Ctrl+C or the process/computer closes. Restart it after Java changes. Refresh the frontend after JavaScript changes. The old src/ApiServer.java is a learning experiment; do not run it alongside Spring Boot because both use port 8080.

Next steps before business use

  1. Visually test the full flow on phone, tablet and desktop, including refresh, server-offline saving and keyboard navigation.
  2. Add real authentication, athlete-specific data ownership, coach authorization and server-enforced subscription entitlements.
  3. Agree with CAP on membership rules, bookings, minors, privacy, cancellation and payment requirements. Finalize the legal documents with qualified review.
  4. Move from local JSON to a database with migrations, backups and transactional multi-user behavior.
  5. Connect planning, bookings and products to Java. Add payment integration only after its provider and business rules are agreed.
  6. Deploy with HTTPS, protected secrets, monitoring and a managed restart policy.

This prototype must not be exposed publicly as a real account-based service yet. It proves the core training workflow while keeping the remaining work explicit.
